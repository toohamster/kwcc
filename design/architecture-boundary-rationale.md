# 架构边界决策 — 服务化、进程化与目标应用形态

> 主题：UI 与业务逻辑是否分离为独立进程（X-Window master/worker 形式）、timer/RPC/MQ 等服务化形态
> 讨论日期：2026-11-04
> 讨论轨迹：性能动机 → 澄清为架构清晰动机 → 两维度拆分 → "工具库不能只看 demo"挑战 → 定位修正 → 目标形态确认 → 最终决策

---

## 决策 1：服务化的正确实现维度是模块边界（进程内），不是进程

### 问题

UI 呈现与业务逻辑同进程同帧执行。是否分离为独立进程（UI 进程专注控件，服务进程专注 timer/RPC/MQ）？

### 决策

服务化 = **模块边界**（Facade+Plugin + bus），默认进程内。master/worker（fork+pipe）承担 CPU 并行维度，不承担架构边界维度。进程化不是服务化的实现手段，是按性质选择性施加的部署手段。

### 原因

- 清晰感（职责单一、可独立开发/测试/替换）来自**职责边界 + 消息通信**，进程内模块可全部获得——kwcc_http 已验证此形态：零引擎依赖 + bus 通信 + 重活 fork 子进程
- IMGUI 同步契约（`ui.*` 同帧返回 bool、view 同帧读 state）跨进程断裂，进程化反而恶化交互延迟（IPC 往返 ≥ +1 帧）
- X-Window 类比错配：X 分离的价值来自**多客户共享一个显示服务器**；kwcc 的 UI 与逻辑同属一个应用，支付 X11 全部成本（IPC 协议/序列化/跨进程调试）拿不到多客户收益
- 经验佐证：Electron / Tauri / VS Code / Qt / 主流游戏引擎——**无一默认 process-per-service**，普遍形态是进程内模块 + 选择性进程隔离，且隔离点高度一致（见决策 3 checklist）

## 决策 2：bus 是唯一耦合点（结构性预留，现在做）

### 问题

将来某服务（尤其插件宿主）需要进程化时，如何避免推倒重来？

### 决策

两条纪律，即刻生效：
1. **服务只通过 bus 与外界通信**——禁止服务间直接函数调用依赖
2. **`ui.*` 同帧同步契约定义为 UI 进程内部契约**——将来跨进程的是 state 快照/事件流，view 层契约不变

### 原因

- 这是**装不回去**的结构属性：耦合点一旦散落成直接函数调用，日后进程化 = 全量重写；工具库必须以成熟期形态为基准做结构预留，不受"当前无证据"否决
- bus 形态即消息边界：将来进程化 = 只替换 bus 传输层（进程内函数调用 → IPC），服务代码零改动
- 零成本：kwcc_http 已是此形态，只是把既有实践纪律化

## 决策 3：进程隔离的架构地位由目标应用形态决定（用户已确认）

### 问题

进程化是"逐服务选项"还是"架构必备"？

### 决策（2026-11-04）

kwcc 目标应用形态（用户确认，两条）：
1. **开发者用 JS 写可信本地应用**
2. **插件/脚本生态**（第三方不可信代码，VS Code extension host 模式）

→ 形态 2 使**插件宿主进程隔离成为架构必备**（不可信代码的崩溃/终止必须不伤宿主，进程是唯一可靠边界）——列为远期路线图项，**现在只做接缝（决策 2），不建进程框架**
→ 形态 1 之下，其余服务按下方 checklist 逐服务判定

### 原因

- VS Code 的核心教训：extension host 独立进程不是性能优化，是**不可信代码隔离的刚需**
- "不做假设性需求"的正确范围是**不提前实施**，不是**不留接缝**——对工具库，接缝属于成熟期必备结构
- 定位依据：kwcc 是工具库，使用者会写出超出 demo 的应用形态；引擎结构要替他们想

### 进程化逐服务判定 checklist（远期使用）

| 条件 | 说明 |
|------|------|
| ① 不可信/易崩溃代码 | 隔离刚需（插件宿主命中此条） |
| ② CPU 密集长期运行 | 真并行需求 |
| ③ 异构语言/运行时 | 服务用非 C/非 mquickjs 实现 |
| ④ 生命周期越界 | 服务需活得比 UI 久（常驻后台） |

命中任一条 → 该服务进程化（bus 传输层换 IPC，服务代码不动）。均未命中 → 进程内 Plugin。
