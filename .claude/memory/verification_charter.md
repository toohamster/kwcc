# 验证与验收章程（Verification & Acceptance Charter）

> **适用范围：每个任务的全生命周期，从问题定义到销账。违反红线 = 严重事故。**
> 立法背景（2026-11-04 X 关闭事故）：方案建立在对死因的猜测上（未取证）；实施后未做行为验证；
> 用"编译通过 + 启动冒烟"冒充验收；修复无效却宣称完成。四个环节全部失守。
> 为杜绝此类系统性失败，立此章程。

---

## 第 0 条：证据原则（贯穿所有阶段）

1. **结论必须携带证据等级标注**：
   - `[事实-来源]`：日志行 / lldb bt / 源码行号 / 实验输出
   - `[假设-待验证]`：推测，必须标注验证方法，**验证前禁止作为方案或代码依据**
   - `[推断-基于X]`：由事实推导，需说明推导链，结论仍需实验确认
2. "应该是" "我猜" "很可能" "理论上" **不构成任何行动依据**
3. **假设台账**：分析阶段显式列出所有假设；每条要么经实验转正为事实，要么显式排除，不得沉默遗忘

---

## 第 1 条：五阶段门禁（每任务必过，任一闸不过不得进入下一阶段）

### Gate-0：问题定义
- [ ] 问题**可稳定复现**（有复现步骤，或复现程序；人工交互类问题必须先构造程序化复现路径）
- [ ] 症状事实已记录（现象、日志、日志终止点），与推测分开存放
- [ ] 不可复现 → **不开工**，先解决复现问题

### Gate-1：根因分析
- [ ] 根因有证据支撑：lldb bt / 日志行号 / 源码行号 / 实验结果（二选一不可时用排除实验）
- [ ] 根因能解释**全部症状**——解释不了的症状 = 分析未完成，继续取证
- [ ] 死亡/崩溃类问题：**必须 lldb 拿 bt**（build_pitfalls.md 方法论），不允许只看日志猜

### Gate-2：方案审定
- [ ] 方案逐条引用根因证据（哪条证据支持哪条改动）
- [ ] **改动点清单 ↔ 验收项映射表**：每条改动对应"怎么验证它生效"
- [ ] 影响范围 + 回退方式已写明
- [ ] 评审逐条验证（API 签名、一致性、可行性），禁止"大概正确"（workflow_rules 6b）

### Gate-3：计划制定（验收标准先行）
- [ ] **验收清单先于实施步骤写定**——先定义"怎么算通过"，再写"怎么改"
- [ ] 验收分级，明确执行人和判定方式：
  - **L1 自动验收**：可执行、可判定、必须贴**实际输出**（不是"通过了"三个字）
  - **L2 用户验收**：写明操作步骤 + 期望现象；只有用户能执行的行为（GUI 点击、视觉、手感）**必须**由用户执行
- [ ] **禁止降级冒充**：编译通过 ≠ 行为正确；启动成功 ≠ 功能正确；冒烟 ≠ 验收；单元过 ≠ 集成过

### Gate-4：实施
- [ ] **写任何测试文件前，必须先重读 `testing_methodology.md` 并逐条对照**：标准 TEST 断言宏模板、测试命名、编译命令模板（tests/bin/ 输出、显式 .o 清单）、测试点自包含、JS_EVAL_RETVAL 用法、TESTING_*.md 记录要求。对照确认后才动手——禁止凭记忆写测试
- [ ] 每步完成**立即跑对应的 L1 验证**，不积累到最后统一验
- [ ] 方案外改动 → 停，回 Gate-2 重新审定（workflow_rules 11）
- [ ] 中间失败如实记录，不跳过、不美化

### Gate-5：结果验证与销账
- [ ] L1 全部通过，**贴实际输出**
- [ ] L2 由用户执行并确认
- [ ] **双过后才可**：更新文档 / memory 销账 / 宣告完成 / 谈提交
- [ ] 任一级失败 → **回 Gate-1 重新分析**，禁止在失败结果上继续叠加修复

## 第 1.5 条：动作前必查文件（强制对照，禁止凭记忆行动）

> 立法依据（2026-11-04）：写测试时凭"会话开头读过"的印象行动，自造断言体系、编译命令三处低级错误——
> 熟悉≠对照，**动手那一刻必须回到文件**。每次执行下表左侧动作前，必须先重读右侧文件再动手。

| 动作类型 | 动手前必查 |
|---------|-----------|
| 写任何测试文件 | `testing_methodology.md` 全文（TEST 宏模板、编译命令模板、tests/bin、自包含、RETVAL、TESTING_*.md） |
| 编译/链接任何东西 | `build_pitfalls.md` + Makefile 实际 flags（不凭记忆拼命令） |
| 调试崩溃/异常行为 | `build_pitfalls.md` 调试方法论（lldb 优先、脚本模板） |
| 出方案 / 提新增 API | `workflow_rules.md` 1b（先读完相关模块 .h，列出已有 API） |
| 改 C 代码命名 | `workflow_rules.md` 2 + `c_architecture.md` 命名规范表 |
| 定大小上限 / 选数据结构 | `workflow_rules.md` 3b（禁止拍脑袋） |
| 涉及 mquickjs API | `mquickjs_c_api.md`（先查此文件，不要重读 mquickjs.h）+ `mquickjs_es5.md`（JS 侧语法） |
| 涉及 microui 行为 | `microui_analysis.md` + 源码行号取证 |
| 涉及 HTTP/IO | `picohttpparser_analysis.md` + `module_dev_experience.md` HTTP 节 |
| 修改方案/新增方案 | `workflow_rules.md` 8b（STATUS.md + README.md + 方案文件三处同步） |
| 任务收尾（测试记录/销账/提交） | `testing_methodology.md` 清理规则 + 章程 Gate-5 + workflow_rules 7（git 确认） |

**违反判据**：动作完成后才发现文件里有现成模板/规则未对照 = 违反本条，记入事故台账。

## 第 2 条：红线（违反任何一条 = 严重事故）

1. **无验收标准宣告完成**——没有事先定义的验收清单，就没有"完成"这个词
2. **以编译/启动/冒烟冒充行为验收**——验证级别必须匹配验收项要求的行为级别
3. **验证造假**——验证失败仍宣称成功、选择性汇报、模糊表述掩盖失败
4. **假设未验证进方案或代码**——猜测驱动的方案本身就是错的，实施越快错得越多
5. **用户专属验收项被顶替**——只有人能验证的行为（点击、视觉、交互），自动化冒烟不算数

---

## 第 3 条：失败处理协议

- **修复无效 = 正常信息**，必须如实报告"未解决"，禁止把失败洗白为成功
- 每次失败必须产出**新事实**（新 bt / 新日志 / 新实验结果），无新事实的重复修复 = 盲改
- **连续 2 次修复无效 → 强制停止**，重新做根因分析，向用户汇报当前全部事实和假设台账，等待指示
- 调试超预期范围（如需要架构级改动）→ 停，汇报，等确认

## 第 4 条：章程自身的演进

- 本章程经实际任务检验，不足处按演进格式追加修订（不覆盖原条款）
- 每次违反事故记入 `module_dev_experience.md`，注明违反的是哪条哪款
- 章程与 workflow_rules.md 冲突时，以更严格者为准
